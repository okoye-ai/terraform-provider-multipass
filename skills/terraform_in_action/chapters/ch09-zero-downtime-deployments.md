# Chapter 9: Zero-downtime deployments

## Core Idea
Don't fight Terraform's force-new destroy-then-create default with lifecycle tricks — achieve zero downtime with Blue/Green environments toggled by a variable (feature flags), or better, offload application deployment to a configuration management tool like Ansible ("better together").

## Frameworks Introduced
- **The lifecycle Block** (three flags, present on every resource):
  - `create_before_destroy = true` — replacement created before old destroyed (no downtime window of 5 min–1 hr)
  - `prevent_destroy = true` — Terraform rejects any plan that would destroy the resource
  - `ignore_changes = [...]` — attributes Terraform ignores in plans (tolerates configuration drift)
  - Caveat: all three alter Terraform's fundamental behavior; use with extreme caution. Winkler: "I do not use create_before_destroy... more trouble than it is worth."
  - Why not default? Many providers can't hold two same-named instances (e.g. S3 bucket names) — namespace collisions
- **Blue/Green Deployment**: two production environments (Blue, Green), exactly one live; router (LB or DNS) points to live; deploy new version to the **idle** environment first, then cutover by flipping the router
  - Analogy: page flipping / double buffering in graphics
  - Ladder: classic Blue/Green → rolling Blue/Green (replace one server at a time; app must handle two versions concurrently; watch schema/data corruption) → canary (percentage-of-traffic ramp with fast rollback, feature toggles by user segment)
- **Terraform + Ansible Two-Stage Pairing**: Terraform provisions infrastructure (static); Ansible configures it and deploys applications (dynamic)
  - Reconciliation of paradigms: Terraform isn't purely immutable (in-place updates, provisioners); CM deploys apps onto mutable infra immutably — the tools are complementary, not competitive
  - Scaling: write VM addresses to a **dynamic inventory file** generated by Terraform (string templates + Local provider)

## Key Concepts
- **Creation-time provisioners gate the lifecycle**: a resource isn't marked created until all creation-time provisioners succeed — the hook for creation-time health checks: `provisioner "local-exec" { command = "./health-check.sh ${self.public_ip}" }` (the `self` object = the resource the provisioner is attached to)
- **Meta argument catalogue** (the complete list, per this chapter): depends_on, count, for_each, provider, lifecycle, provisioner/connection
- **Terraform-generated SSH keys**: TLS provider for the keypair → `local_file` with `sensitive_content` + `file_permission = "0400"` → `aws_key_pair` with the public half
- **remote-exec + connection block**: install Ansible on the box inline, then sequentially (provisioners force ordering) run the playbook via local-exec; the output `ansible_command` lets you redeploy apps without any re-apply
- **The cutover**: changing `var.production` from `"green"` to `"blue"` only modifies the LB listener target group (~2 changes, seconds); instant from the user's perspective
- **Blue/Green considerations**: scale idle env down for cost (scale up pre-cutover); reduce blast radius by splitting into 3 workspaces (base/blue/green); canary possible with Route 53 two-LB traffic weighting

## Code Examples
```hcl
# ZDD-lite: force-new with create_before_destroy + creation-time health check
resource "aws_instance" "instance" {
  ami = var.ami
  instance_type = "t3.micro"
  lifecycle { create_before_destroy = true }
  user_data = <<-EOF
    #!/bin/bash
    echo "App v${var.version}" >> /var/www/index.html
    python3 -m http.server 80
  EOF
  provisioner "local-exec" { command = "./health-check.sh ${self.public_ip}" }
}

# Blue/Green in Terraform = two autoscaling modules + a routing variable
variable "production" { default = "green" }        # flip to "blue" to cut over
module "base"   { source = ".../base"; production = var.production }
module "green"  { source = ".../autoscaling"; app_version = "v1.0", label = "green", base = module.base }
module "blue"   { source = ".../autoscaling"; app_version = "v2.0", label = "blue",  base = module.base }
```
- **What it demonstrates**: Blue/Green with feature-flag cutover — the recommended Terraform-native approach (the plan shows only `~` changes to the LB action's target_group_arn)

## Worked Example
Terraform+Ansible handoff end-to-end:
1. `tls_private_key` → private key .pem (0400) + `aws_key_pair`
2. `aws_security_group` on the default VPC: :22 (SSH) and :80 (HTTP)
3. `aws_instance` with remote-exec provisioner (connection: ssh/user ubuntu/host self.public_ip/private_key) installing Ansible, then a local-exec provisioner running `ansible-playbook -i '${self.public_ip},' app.yml`
4. Modify `index.html` (green-v1.0 → blue-v2.0) and re-run the output `ansible_command` — application updated with zero Terraform involvement

## Key Takeaways
1. Default force-new behavior = downtime between destroy and create; lifecycle changes it but at the cost of reasonability.
2. Prefer Blue/Green workspaces/feature flags over create_before_destroy for cutover-style releases.
3. Databases belong in the base (shared) layer for Blue/Green — stateful data across environments is notoriously tricky.
4. remote-exec+local-exec provisioners are the one defensible combo: they guarantee Ansible runs after install (no race) with logs in Terraform stdout.
5. Ask "is Terraform the right tool for the job?" — above the infrastructure layer, the answer is usually no.
