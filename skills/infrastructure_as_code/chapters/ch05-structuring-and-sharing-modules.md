# Chapter 5: Structuring and sharing modules

## Core Idea
Treat shared modules like software artifacts with their own life cycle: pick a repository structure (single, multiple, or a mix), version modules with semantic versioning and version pinning, release them only after testing in a dedicated environment, and share them with opinionated defaults plus a review gate.

## Frameworks Introduced
- **Single repository structure (mono repository / monorepo)**: contains all IaC (configuration and modules) for a team or function.
  - When to use: tens of modules, a few environments, a build system that can handle nested subdirectories (Bazel, Pants, Yarn).
  - How: two top-level directories — `environments/` (subdivided by team, then development/production) and `modules/` (subdivided by provider, e.g., `modules/gcp`). Reference modules by local path. Benefit: singular view; compare environments by diffing files. Limitations: cannot limit editor access to one module or environment; CI must recursively search every directory (a Jenkins run took three hours); a change to one module can break dependents.
- **Multiple repository (multi repo) structure**: separates IaC (configuration or modules) into different repositories based on team or function.
  - When to use: hundreds of modules/environments, need granular access control (contractors see only their team's config), CI that must run per-repo workflows in parallel.
  - How: one repository per module (`gcp-network-module`, `gcp-tags-module`, ...); configurations reference module repos via package managers (`pip install -r requirements.txt` with a git URL and tag). Benefits: independent module life cycles, parallel CI, access control. Limitations: no singular view; conformance drift (solve with a prototype module of lint/format tests pulled by CI); troubleshooting requires searching each module repo for inputs/outputs; docs and formatting updates must touch every repo.
- **Mixed repository strategy**: a multi repo for shared, reusable modules plus a single repo for application-unique configuration.
  - When to use: composable/reproducible modules go to their own repos; specialized configurations that need evolvability stay local (e.g., the Fruits team's queue module).
- **Module repository naming convention**: `<infrastructure provider><resource type><tool/purpose (optional)>` — e.g., `gcp-server-module`. Descriptive enough for a teammate to identify; works for folders in a single repo too.
- **Semantic versioning for modules**: tagging iterations of code (git tags or artifact-repository labels) so consumers pin versions.
  - When to use: any module consumed by other teams, to preserve evolvability and enable auditing/deprecation of stale versions.
  - How: tags are the contract; pin versions, never reference "latest."
- **Module release process**: deploy the change → test the module in a dedicated environment → tag the release with a version → optionally package and push to an artifact repository or storage bucket → update documentation/release notes.

## Key Concepts
- **Repository structure**: how IaC is divided across code repositories (single vs. multiple vs. mixed).
- **Versioning**: the process of assigning unique versions to iterations of code.
- **Version pinning**: referencing an exact module version (tag) in configuration; preserves idempotency — pinned IaC should not detect drift.
- **Releasing**: the process of distributing software (a module) to a consumer, only after tests certify it works.
- **Release notes / changelog**: a document listing changes for a release, especially breaking changes to inputs and outputs; best generated by an automated semantic release tool from commit messages (e.g., `feat(security): store password in secrets manager` bumps the major version).
- **README**: repository document explaining usage and contribution; for IaC it documents a module's purpose, inputs, and outputs — enforce its existence with a linting rule.
- **Helper files**: metadata files a tool or language needs (`__init__.py`, `setup.py`) — standardize them across the organization so automation can search/update them.
- **Opinionated defaults**: module inputs with prescriptive, secure defaults so even teams that don't know the resource get a secure, working one; flexibility via overriding or updating the module.
- **Prototype module**: a module containing all formatting/linting tests for module repositories, downloaded by CI to enforce standards across hundreds of repos.
- **DRY (don't repeat yourself)**: pursue reuse, but you cannot fully comply in infrastructure — occasional repetition buys clearer configuration within tool/platform limitations.
- **Self-service with governance**: any team may propose module updates; module approvers review before release; disruptive changes need a subject-matter expert.

## Mental Models
- Use a single repo when a singular view matters more than access control; use multiple repos when scale and granular access control matter more — and expect to refactor as you grow.
- Think of a shared module as an artifact, like an application library, container image, or VM image: versioned, released, documented, deprecated.
- Treat version tags as contracts between the module and every team that pins it.
- Balance self-service with review: approval gates catch disruptive changes before they hit consumers, not after.

## Anti-patterns
- **Referencing the latest module version**: you can't predict what a module update changes; pin exact versions.
- **Version jumping**: upgrading across many major/minor versions at once raises the risk and failure rate; upgrade within a few minor version changes.
- **Releasing untested modules**: a module that breaks one team breaks every team that shares it; test in a dedicated environment (separate account or project) first.
- **No conformance enforcement across many repos**: without a prototype module of lint/format checks, older modules (like a seldom-updated DNS module) drift from standards.
- **Unopinionated shared modules**: without defaults, each team invents its own configuration, undermining security and standardization.
- **Letting teams merge disruptive changes without SME review**: e.g., a PostgreSQL 12 upgrade that deletes the old database and creates an empty one; a database administrator must document the migration path first.

## Code Examples
```text
# Listing 5.2 — requirements.txt references module repositories, pinned by tag
-e git+https://github.com/joatmon08/gcp-tags-module.git@1.0.0#egg=tags
-e git+https://github.com/joatmon08/gcp-network-module.git@1.0.0#egg=network
-e git+https://github.com/joatmon08/gcp-server-module.git@0.0.1#egg=server
-e git+https://github.com/joatmon08/gcp-database-module.git@1.0.0#egg=database
```
- **What it demonstrates**: a multi-repo setup: the package manager downloads each module from its own repository at a pinned tag, installed with `pip install -r requirements.txt`.

```python
# Listing 5.3 — importing released modules into an environment configuration
from tags import StandardTags
from server import ServerFactoryModule
from network import NetworkFactoryModule
from database import DatabaseFactoryModule
import json

if __name__ == "__main__":
   environment = 'production'
   name = f'{environment}-hello-world'
   tags = StandardTags(environment)
   network = NetworkFactoryModule(name)
   server = ServerFactoryModule(name, environment, network, tags.tags)
   database = DatabaseFactoryModule(
       name, server, network, environment, tags.tags)
   resources = {
       'resource': network.build() + server.build() + database.build()
   }
   with open('main.tf.json', 'w') as outfile:
       json.dump(resources, outfile, sort_keys=True, indent=4)
```
- **What it demonstrates**: after the package manager downloads the modules, environment configuration composes them; consistent modules for development and production prevent drift between environments.

## Reference Tables

| Aspect | Single repository | Multiple repositories |
|---|---|---|
| View of all IaC | One place; easy to compare environments | Must reference each module individually |
| Editor access control | Cannot limit per module or environment | Granular, per-module/team |
| CI | Recursively searches every directory; slows with scale (`Jenkins took ~3 hours`) | One pipeline per repo; runs in parallel, scales faster |
| Module life cycle | Everyone can change any module; breaking dependents likely | Independent evolution and versioning per module |
| Conformance to standards | Easy (one repo) | Needs a prototype module of checks |
| Troubleshooting a failure | Easy | Extra search effort for module inputs/outputs |
| Docs/formatting updates | One change | Must update every module repo |
| IaC principle served | Composability, reproducibility | Evolvability |

## Worked Example
Secrets-manager migration for the soil-monitoring database, end to end:
1. **Trigger**: the security team requires rotating database passwords every 30 days via a secrets manager; every team uses the database module, which currently outputs the password.
2. **Pin v1.0.0**: tag the current module (`git tag v1.0.0`, `git push origin v1.0.0`) and have all teams (Fruit, Leafy Greens, Grain, Herb) pin to v1.0.0 — no drift, no change while everyone migrates.
3. **Build v2.0.0**: rewrite the module to store the password in the secrets manager; it now outputs the endpoint and the secrets-manager path (`/secrets/my-database`) instead of the raw password. Tag v2.0.0.
4. **Pilot**: the volunteer Fruits team tests v2.0.0, refactoring its IaC to fetch the password from the secrets manager.
5. **Release**: tag the release, optionally package it into an artifact repository/S3 bucket, and generate release notes (`feat(security): store password in secrets manager` → major bump in semantic-release tooling).
6. **Discipline**: v1.0.0 is not deleted immediately — consumers upgrade within a few minor versions, and stale versions get deprecated on a timeline.

## Key Takeaways
1. Choose the repository structure by CI scalability and access-control needs; start single for tens of modules, refactor to multi-repo when CI runtime or access limits bite.
2. Standardize repository naming as provider + resource + purpose (`gcp-server-module`) across both structures.
3. Never reference latest: pin versions with tags, and pin before refactoring the module.
4. Bump the major version for removed inputs/outputs/resources; minor for input/output changes that don't break previous consumers; patch for scoped configuration tweaks.
5. Release only after testing in a dedicated environment (separate account/project), then tag, optionally package to an artifact store, and write release notes.
6. Enforce module standards with a prototype module of lint/format tests and lint for README existence — README documents purpose, inputs, outputs.
7. Set opinionated defaults in shared modules and let any team propose updates, pausing release for approvers and pulling in subject-matter experts for disruptive changes.
