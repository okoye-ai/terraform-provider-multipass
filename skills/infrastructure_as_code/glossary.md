# Glossary — Infrastructure as Code (Rosemary Wang)

- **Active-active configuration** — two or more environments each taking traffic, so one can fail without an outage (Ch 9)
- **Active-passive configuration** — one environment takes traffic while a duplicate stays warm for failover (Ch 9)
- **Adapter pattern** — dependency pattern that transforms metadata from one resource into a form another can use; best across providers or prototype modules (Ch 4)
- **Blast radius** — the scope of impact a failed change has on surrounding resources; smaller modules and higher-level resources shrink it (Ch 1, 3, 4, 10)
- **Blue-green deployment** — building a duplicate "green" environment, testing it, shifting traffic to it, then deleting the old "blue" one (Ch 9)
- **Break-glass change** — an emergency access or deployment path used only when normal controls would fail operations (Ch 8, 11)
- **Brownfield** — existing infrastructure migrated to IaC, as opposed to greenfield (Ch 2)
- **Builder module** — module that decides *which* resources to create; can be composed of factory modules (Ch 3)
- **Canary deployment** — shifting a small slice of traffic (~default 10%) to new infrastructure, holding a regression window between increments (Ch 9)
- **Change type** — Wang's three: standard, emergency, and new/major change; each maps to a different delivery approach (Ch 7)
- **Circular dependency** — two resources each depend on the other's attributes; chicken-or-egg creation problem (Ch 4)
- **Code as documentation** — the IaC itself communicates what infrastructure exists and why (Ch 1)
- **Composite pattern** — module pattern that groups resources into a hierarchy for automation as one unit (Ch 3)
- **Composability** — you can assemble any combination of resources and update each without affecting the others (Ch 1)
- **Configuration drift** — deviation from the desired configuration in version control to the actual configuration (Ch 1, 11)
- **Continuous delivery (CD)** — every commit passes automated tests and deploys to production-like envs; production applies are semi-automated (Ch 7)
- **Continuous deployment** — every commit automatically deploys to production, with tests as the only gate (Ch 7)
- **Continuous integration (CI)** — every commit is merged, tested, and validated against shared trunk (Ch 7)
- **Copyleft license** — license (e.g. GPL) requiring you to release modifications of the code (Ch 13)
- **Cost driver** — a resource attribute with outsized bill impact; model only the dominant ones (Ch 12)
- **Cost estimation** — automating bill prediction by parsing IaC and multiplying against the provider's billing catalog (Ch 12)
- **Declarative style** — stating the final state; the tool figures out how to reach it (Ch 2)
- **Delivery pipeline** — automated workflow to build, test, deploy, and release infrastructure changes (Ch 7)
- **Dependency injection** — high-level resource calls a low-level one and parses its object structure; combines inversion of control + dependency inversion (Ch 4, 10)
- **Dependency inversion principle** — the high-level resource should use an *abstraction* of low-level resource metadata (Ch 4)
- **Dry run** — pre-apply change preview (e.g. `terraform plan`) used to catch drift and unintended effects before applying (Ch 1, 6)
- **Ephemeral resource** — short-lived, cheaper resource types (spot/preemptible) for interruptible workloads (Ch 12)
- **Event-driven IaC** — automation triggered by infrastructure events (scaling, expiration, drift) rather than a pipeline run (Ch 13)
- **Evolvability** — the configuration accommodates growth without early, unnecessary optimization (Ch 1)
- **Facade pattern** — simplified interface exposing one or two outputs from a low-level module to many high-level consumers (Ch 4)
- **Factory module** — module that takes inputs and configures resources with specific, opinionated attributes (Ch 3)
- **Feature flag** — toggle (default off) that stages a change so it can be rolled out or removed safely (Ch 10)
- **Feature-based development** — branching model where work happens on feature branches (feature branching, Git Flow) (Ch 7)
- **GitOps** — version control as the source of truth; infrastructure events and changes are automated as commits to main (Ch 7, 13)
- **High-level resource** — a resource that depends on another resource or module (Ch 4)
- **Idempotency** — running automation repeatedly yields the same end state without affecting the resource (Ch 1)
- **Infrastructure dependency** — relationship in which a resource depends on the existence and attributes of another (Ch 4)
- **Inversion of control** — the high-level resource calls the low-level one to request attributes, rather than the low-level pushing values (Ch 4)
- **Least privilege** — grant only the access a resource or person needs; implement via role factory modules (Ch 8)
- **Low-level resource** — a resource other resources depend on; changes here have the largest blast radius (Ch 4)
- **Mediator pattern** — pattern that organizes dependencies among many modules and orchestrates create/update/delete; most IaC tools act as the mediator (Ch 4)
- **Module** — a group of infrastructure resources managed as a unit ("module" ≈ stack/set of resources) (Ch 3)
- **Monolithic architecture for IaC** — all resources in one configuration and one state file; distinct from monorepository (Ch 10)
- **Mutable vs. immutable infrastructure** — modifying servers in place vs. replacing them from images; IaC favors immutability (Ch 2)
- **Opinionated defaults** — the shared standard attributes a module applies unless overridden; enable self-service with governance (Ch 5)
- **Out-of-band change** — change made outside IaC (manually through the console); remediating these is a core IaC practice (Ch 2)
- **Permissive license** — license (e.g. MIT) allowing fork and modification with attribution (Ch 13)
- **Policy as code** — codified compliance rules evaluated as tests against IaC ("shift-left security testing") (Ch 8)
- **Policy engine** — tool that evaluates IaC against policy (OPA, Sentinel, CloudFormation Guard, InSpec, Kyverno, CrossGuard) (Ch 8)
- **Prototype module/pattern** — module that exports static default configuration (tags, labels) without creating resources (Ch 3, 8)
- **Refactoring IaC** — restructuring configuration without impacting existing deployed resources (Ch 10)
- **Regression test** — periodic test that re-verifies a system still works, catching drift between test runs (Ch 6, 9)
- **Reproducibility** — the same configuration reproduces an environment or resources identically (Ch 1)
- **Resource expiration tag** — tag marking a resource's renewable lease; pipeline runs renew it (Ch 12)
- **Rolling forward** — reverting by deploying a new working state (immutability), not restoring the old one (Ch 11)
- **Rolling update** — updating a set of resources a few at a time to reduce blast radius (Ch 10, 13)
- **Secret** — credential or sensitive value; passed from a secrets manager, never in version control (Ch 2, 8)
- **Singleton pattern** — module pattern for exactly one instance of rarely changed infrastructure (Ch 3)
- **Smoke test** — quick end-to-end check that a system is alive after deployment (Ch 6)
- **Software supply-chain attack** — compromise introduced through a third-party tool or dependency; mitigated by pinning and mirroring (Ch 13)
- **State import / state removal** — moving resources into a tool's state (`terraform import`) or handover ownership out of it (`terraform state rm`) (Ch 10)
- **Static vs. dynamic analysis** — checking IaC without running it (lint, policy) vs. testing after applying it (Ch 6, 8)
- **Testing environment** — persistent environment similar to production where integration/e2e tests run (Ch 6)
- **Tool state** — the IaC tool's stored representation of infrastructure state (e.g. `terraform.tfstate`), which can itself drift from actual state (Ch 4, 13)
- **Trunk-based development** — branching model where small changes merge directly to main several times a day (Ch 7)
- **Unidirectional dependency** — one-way relationship in which only one resource refers to another (Ch 4)
- **Version pinning** — consuming modules at an exact version tag; never reference "latest" (Ch 5)
